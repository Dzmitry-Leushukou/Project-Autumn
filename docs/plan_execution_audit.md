## Подтверждённые дефекты

### 1. P1 — посадка на кольце не учитывает направление выбранного маршрута

Место: `core/simulation.py:580–590`, кодирование допустимости поездки в `core/simulation.py:434–457`.
Связанные требования: 6.3, 8.2, приёмка спринта 3 и критерий 14.3.

Проверка посадки использует id ветки и наличие станции назначения впереди. На кольце впереди
есть любая другая станция, независимо от направления. Поэтому для поездки A→B подходит также
поезд A→D→C→B, хотя граф маршрутов выбрал прямой участок A→B.

Воспроизведено без шума спроса и случайных задержек, с проверкой инвариантов каждого события:

```python
from tests.test_movement import small
from data_io.schema import OD
from core.simulation import Simulator

n = small([["A", "B", "C", "D"]], (0,), fleet=2, headway=180)
n.lines[0].depot_station = "B"
n.settings.demand_noise = False
n.settings.delays.p0 = 0
n.od_matrix = [OD(origin="A", destination="B", start_min=300, len_min=2, trips=10)]
s = Simulator(n, check_invariants=True)
r = s.run()
```

Выбранный маршрут: `('A', 'B')`. Все 10 пассажиров садятся на станции A в поезд №1 направления −1
в 18075 с; его следующий перегон — **A→D**, отправление в 18096.6667 с.
Маршрут, по которому рассчитывалась вероятность выбора, расходится с фактической перевозкой.
Это способно исказить очереди, загрузку и оценку расписаний на кольцевых сетях.

Исправление: проверять покрытие оставшегося участка поездки фактическим направлением поезда,
включая циклический порядок станций. Добавить регрессию с двумя направлениями кольца,
когда поезд неподходящего направления приходит первым.

### 2. P2 — часть метрик оптимизации возвращается только для первого seed

Место: `optimizer/evaluation.py:88–127`. Требования: 8.5, 9.2, 9.4.

`metrics` сначала копируется из первого прогона, затем усредняются только перечисленные скаляры
и некоторые поля `line_periods`. Тепловая карта и `actual_headways` сохраняются от первого seed.
Таким образом, результат объединяет усреднённые W/D/LF и значения другого статистического смысла
без соответствующей пометки.

На `small()`, seeds `[42, 43]`, очередь станции A / capacity равна соответственно
`0.0125` и `0.01625`. Результат `Evaluator.many` возвращает `0.0125`, тогда как среднее —
**0.014375**. Усреднение W в этом же результате выполнено правильно. Дефект не означает,
что f_A и f_B рассчитаны только по первому seed: обе целевые функции усредняются.

Исправление: определить и реализовать агрегацию вложенных метрик по ключам ветки/направления/
периода/станции/перегона; диагностические поля отдельного прогона явно отделить от средних.

### 3. P2 — показатель «Ожидают» отстаёт от выбранного времени до минуты

Место: `web/src/App.tsx:299–307`. Требования: 13, просмотр состояния в выбранный момент.

Панель использует `series[floor((time-start)/60)]`, а карточка станции на Canvas восстанавливает
очередь по точным `queue_events`. Это разные состояния при изменении очереди между минутными
снимками. Проверка основана на коде панели и фактической траектории, отдельный браузерный
сценарий с этим конкретным набором не запускался.

В примере из дефекта №1 при выбранном времени **18100 с** панель использует снимок **18060 с**
и показывает **10** ожидающих. По `core.trajectory.state_at(trajectory, 18100)` ожидающих уже **0**:
посадка завершена в 18075 с.

Исправление: считать показатель по тем же дельтам очередей, что использует карта,
или явно обозначить минутную точность показателя. Проверить перемотку между снимками.

## Оговорки и незавершённые пункты

1. Разрыв 3 с честно описан в `performance.md` и `progress.md`; критерий **14.4 допускает**
   такую документированную оговорку. Поэтому этот разрыв отдельно не трактуется как скрытый
   провал всей приёмки, хотя сам численный бюджет не выполнен.
2. `optimizer/nsga2.py:105,115,143,168` проверяет время между пакетами, а финальную переоценку
   выполняет целиком. Строгого верхнего ограничения 60 с нет. В текущем замере бюджет выполнен.
3. При wall-clock остановке одинаковый seed не фиксирует число оценённых особей.
   Тесты доказывают побитовое совпадение для фиксированных поколений и между 1/2 процессами,
   но не общее требование повторяемости результатов при остановке по времени. Ограничение
   уже описано в пункте 7 `decisions.md`; его документирование не равно выполнению строгого требования.
4. `docs/london_data_audit.md:28` и раздел ограничений прямо сообщают о незавершённой
   независимой проверке дверей. Текущие данные спроса реальные; прежний synthetic fallback
   не описывает активную сеть. OD модельная, интервалы/длины — оценки, парк/физика — допущения.
   Внешние сайты и исходный Excel заново в этой проверке не скачивались; проверены сохранённые
   источники, код импорта и тесты. Платформенные двери нельзя считать перепроверенными.
5. `optimizer/train_count.py:91` возвращает общее объяснение возможных расхождений,
   а не диагностику того, какие факторы сработали именно в выбранном расчёте (9.5).
   Оба режима расчёта работают; содержательная диагностика причин реализована частично.
6. Linux CI и совместимость с другими поддерживаемыми Python не запускались заново.
   В репозитории есть workflow и ссылки на предыдущие успешные прогоны; новый результат
   удалённого CI в этом аудите не заявляется.
