# Формат сети 1.0

Полная машинная схема: `data_io/network.schema.json`. Примеры: шесть JSON в `datasets/synthetic/`. Это единственный формат сети; CSV импортирует только спрос.

Обязательны `meta` (name, synthetic), `stations` (id, name, x, y), `lines` (id, name, color, stations), `segments` (from, to и length_m или run_time_s), `fleet`, `demand`. Координаты 0–1000, время в секундах от полуночи, demand.start_min/len_min в минутах. Число периодов = ceil((day_end_s-day_start_s)/(period_len_min*60)). Кольцо замыкается без повторения первой станции.

Числовое значение допускает запись `{"value": 750, "source": "estimate"}`. Источники: data / estimate / assumption / user. Число без тега — явное пользовательское значение, а не свидетельство реальных данных. Отчёт валидатора содержит `sources` по путям JSON. Применённые defaults перечислены в `assumptions`; незаданные обязательные параметры — в `missing` и `errors`. `fleet_assignment` можно опустить: он будет вычислен по времени оборота, с явным источником assumption. Пропуски спроса означают 0 и дают предупреждение, не ошибку (конкретное правило раздела 5).

Отчёт: `errors`, `warnings`, `missing`, `assumptions` — списки `{path,message,...}`. Ошибки блокируют расчёт. Нормализованная модель хранится отдельно от исходного JSON; read/write сохраняют исходные теги без потерь.

Минимальный фрагмент записи перегона: `{"from":"A","to":"B","length_m":{"value":900,"source":"user"}}`. Полный минимально изменяемый пример — `a_simple.json`.

`settings.optimizer.evaluation_budget` — дополнительный воспроизводимый лимит оценок расписаний, целое ≥4, default 20 (`assumption`). `population` и `generations` остаются верхними границами размера популяции и поколений. При малом лимите начальная популяция ограничена половиной лимита (не меньше 4), чтобы оставить оценки для эволюции. Точный исходный вариант оценивается отдельно, повторные сценарии берутся из кэша. `time_budget_s` служит аварийным пределом времени; результат содержит `stop_reason`, `reproducible` и список полностью оценённых `evaluated_candidates`.

В результатах оптимизации все измеряемые поля метрик усредняются по seed. Строки фактических интервалов объединяются по `(line,direction,period)`, а периодные показатели по `(line,period)`. Отсутствующие проходы/блокировки в тепловой карте дают нулевой вклад; отсутствующий фактический интервал не заменяется нулём секунд. Число выпусков усредняется по всем seed, интервал — по имеющимся наблюдениям; если наблюдений нет, остаётся null.

`POST /train-count` дополнительно возвращает `diagnostics`: измеренные `boarding_s`, `random_delay_s`, `blocking_s`, `shared_blocking_s` (поезд-с за выбранный период), `passenger_exchange`, `release_delay_s`, `denied_share`, `releases`, проверенные `headway_s` и `trains`. При пустом диапазоне из-за ограниченного парка `diagnostics=null`, причина явно указана в `explanation`.

Траектория дополнительно содержит `queue_directions`: события `{time, station, towards, delta}`, где `towards` — id следующей станции ездового участка, а `null` — отсутствие доступного маршрута. Это разбиение общей очереди `queue_events`, не дополнительные пассажиры. На общем участке группы учитываются один раз независимо от числа обслуживающих веток. События агрегируются по моменту, станции и следующей станции; накопление дельт позволяет перематывать таблицы в обе стороны.

`trajectory.trains` — список всех назначенных составов `{train, line, station, direction}` с нумерацией с нуля, стартовой станцией и направлением. Поезда без поездок остаются в списке. В `stops` поле `ready` задаёт момент окончания стоянки до возможного ожидания свободного перегона; фактический `departure` может быть позже. UI получает текущую фазу по временным интервалам `trips`/`stops`, а округление количества пассажиров выполняет только при отображении.
